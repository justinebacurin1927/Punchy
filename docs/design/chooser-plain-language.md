# App chooser and clearer wording — 2026-11-24

Jaycee requested a modern replacement for the gray app-selection dialog, simpler explanations for users who are not tech-savvy, removal of the unnecessary network footer, and a GitHub README with the Punchy logo.

The picker follows the existing near-black/neon identity: rounded26dp panel,20dp inset,22sp title,16sp names, actual36dp app icons,24dp rounded checkmarks and64dp-or-taller rows. Search narrows the list without losing choices; selected apps start first. A count reflects selectable apps, while saved choices for apps absent from the list are preserved. Package identifiers appear only to distinguish duplicate app names. Native checkable accessibility state and a visible mark express selection without relying only on color. Cancel/Back/outside discard drafts; only Save writes preferences. The list scrolls independently with actions below it. The picker uses the available window height so Android can shrink it above the keyboard; a fixed pixel-height floating window hid its footer even while accessibility nodes reported the buttons present. Final validation compares actual button bounds with the keyboard region, not node presence alone. Animation-disable behavior follows the existing press helpers.

The normal detection screen shows a heading, a short explanation/next step and last-check time. Music-only notifications no longer spill raw media fields into that view. The explicit Copy detection report action retains the existing technical payload, still excluding filenames and message bodies. Setup/alignment help uses everyday wording; the main network footer is removed. The README leads with the original black/neon Punchy mark, a download link and simple setup.

Evidence/limits: existing ROSS diary/mobile/type/visual standards and the approved v0.1.3 design apply. [Android accessibility guidance](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views) supports labeled48dp+ targets; [editable-field guidance](https://developer.android.com/guide/topics/ui/accessibility/principles) supports explicit search hints. Automation cannot establish that every user understands the wording; actual render and phone feedback remain necessary. No media/download parsing or permission change is included.

Validation is focused on the changed picker/status paths and data-preserving upgrade; the prior83-check video/glass flow is not rerun for an unchanged island/core.
